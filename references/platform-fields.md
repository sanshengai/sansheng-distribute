# 平台填写项矩阵（标题 / 简介 / 话题 / 合集 / AI 声明 / 原创 / 封面 / 活动）

用途：封存前确认每个平台、每条路线哪些字段由代码自动填写并读回，哪些只能靠执行器按清单逐项操作，哪些该路线根本不支持。机器可读版是 `assets/platform-fields.json`，`scripts/fields_check.py` 用它在封存前报告缺项；不支持的字段会被显式列出，不再沉默。

模式：
- **自动读回**：核心/内置引擎填写，并有独立读回核对该字段。
- **清单逐项**：执行器（Agent）按本清单在页面逐项操作；Skill 读回不覆盖或只覆盖部分，须另留截图/字段证据。
- **不支持**：该路线无法设置；需换路线补齐，或在回执中记为缺口。
- **无此项**：平台没有该选项，不要求填写。

## 已知缺口（必须在回执中写明，不能静默）

- **B站 CLI**：只有投稿标签，没有原生话题；不归入合集；不参加活动。需要这三项时走网页补齐（见下）或在回执记“未设置”。
- **视频号、支付宝**：全部字段靠执行器清单逐项；Skill 读回只证明作品存在/标题/状态，话题、合集、声明、原创须另留页面证据。
- **微博**：本路线不设合集/活动。
- **YouTube**：视频清单本身不含封面与播放列表；它们是 `youtube-bundle-*`/`youtube-component-*` 组件，须各自 verified。
- **X**：井号只是正文文本，不登记为原生话题。

## B站网页补齐原生话题与合集：可行性（2026-11-02 调研，未实测）

- 原生话题：网页投稿接口 `x/vu/web/add/v3` 有可选 `topic_id`/`mission_id`；固定版 biliup 已用 `--extra-fields` 传 `creation_statement`，同一机制理论上可传 `topic_id`。前置：先用话题查询接口拿到真实 ID，并在读回里核对话题实体。**结论：可行性高，需一条授权测试稿验收后才能开启。**
- 合集：不是投稿字段，是投稿后的独立接口 `x2/creative/web/season/section/episodes/add`（需 section_id、aid、cid），合集创建另有人工审核。**结论：可作为发布后“组件任务”（类似 YouTube playlist 组件），需新增核心组件、独立读回 `x2/creative/web/seasons`，并先验收一次；在实现前，用网页创作中心“合集管理”逐项手动加入并截图留证。**
- 活动：`mission_id` 同上，需资格判断，保持清单逐项。
- 以上均基于公开整理的接口文档（bilibili-API-collect），不是官方开放平台承诺；账号与合集 ID 只放私有配置。

## 每集每平台逐字段核对表（复盘必填）

封存前运行：

```
python3 scripts/fields_check.py --platform <平台> --copy <文案或spec.json>
```

退出码 1 表示缺项，补齐后再封存；`unsupported` 列表照抄进回执。发布后在复盘里每集每平台填一行：

| 集 | 平台 | 标题 | 简介 | 话题(实体/文本) | 合集 | AI 声明 | 原创 | 封面比例 | 活动 | 证据 |
|---|---|---|---|---|---|---|---|---|---|---|

每格写 自动读回✓ / 清单✓(证据) / 不支持 / 无此项 / ✗(原因)；不得留空。
