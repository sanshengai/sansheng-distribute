# 分发耗时计量

执行和恢复时，核心在同一个私有 SQLite 账本记录 `preflight`、`execute`、`continue`、`verify` 的时间、结果和耗时。不额外安装计量服务，不把计量当作授权或平台成功回执。

```sh
python3 scripts/publish.py --profile /private/profile.json --state-dir /private/state metrics --key JOB_KEY
```

此命令只查询指定任务的计量，不调用平台、不触发重传。批次按 `batch-status` 中各目标的 key 分别查询，不把并行目标的累计耗时冒充整批墙钟耗时。

- 时间戳为 UTC，耗时为单调时钟测得的整数纳秒。`phases` 汇总每个阶段的样本数、成功/失败数和累计耗时；`samples` 保留各次执行、核验和恢复记录。
- `completed` 表示该阶段返回且首次观察已保存，不代表整个平台已公开。审核状态、内容核验和作品 ID 仍以原任务账本为准。
- 执行阶段先持久保存实际受理 ID，再记录计量。计量数据库写入失败不替换原结果或原错误，不释放未知任务锁，也不触发重发。
- 旧任务、进程被强制终止或计量写入失败可能没有样本。空集合表示未测得，不能解释为零耗时；不为历史任务补造数字。
- 阶段耗时包含适配器启动、平台通信/等待和保存首次观察。不能据此拆出上传与转码耗时、Agent 操作、截图次数或人工介入；这些维度需要当次另有实际记录。

做效率对照时，保留输入大小、网络、目标平台和动作范围，分别记录上述未自动计量维度。复用真实授权任务，不能为计时额外重复公开投稿。没有可比基线时只报告观测值，不宣称提速比例。

## 已取得的实测样本

2026-10-26，统一 B站适配器在一个真实账号上传四秒技术片及封面：本地预检 0.111 秒，执行至保存受理 ID 3.513 秒；最终一次后台和公开页核验 0.711 秒。全程只上传一次，核验沿原稿件恢复。首次执行到最终核验的墙钟约 219 秒，包含排查封面核验缺口及开发时间；不能把它说成纯审核耗时，也不能将阶段时间相加宣称“约四秒发布成功”。没有同条件浏览器基线，不计算提速百分比。这一小文件样本不代表常规长视频的上传耗时。
