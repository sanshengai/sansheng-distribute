# B站评论只读候选

`scripts/bilibili_comments_candidate.py` 显式启用后，将指定的本人作品评论写入现有互动收件箱。使用既有私有 Cookie，仅发 GET，不刷新登录、不安装第三方包、不拟稿或发送。它使用第三方网页协议，不是 B站公开承诺的官方评论 API，不能据此开启无人值守。

## 账号和监测范围

私有配置需为当前用户持有的 `0600` 普通 JSON 文件，不能放进公开仓。示例值须替换为实际账号和已核验的作品身份：

```json
{
  "enabled": true,
  "account": "creator",
  "uid": "123456",
  "credentials": "/private/auth/bilibili.json",
  "not_before": "2026-01-01T00:00:00+00:00",
  "works": [{"aid": "987654321", "bvid": "BV1AA411A7gJ"}]
}
```

`enabled` 默认未配置，不主动运行；须明确列出 1 至 20 个作品。身份来自分发账本与平台，不能按标题猜。每次检查先核对真实登录 UID，再核对全部指定作品的 UID、aid、bvid；任何不符均拒绝读取评论，不扩大到其他作者。未知字段、空作品、重复作品、未来或无时区的监测起点均拒绝。

`not_before` 是监测起点。首次读到的更早评论保留为历史上下文和基线，本地标作 handled，不进入新留言拟稿；这不代表已回复。监测起点之后的子回复，即使挂在旧根评论下，仍作为新留言进入队列。重复同步保留作者已经处理的状态，不将旧留言重新打开。需要主动处理历史留言时须另外显式选择，不为展示效果集中补回多年旧评。

## 一次只读同步

```sh
python3 scripts/bilibili_comments_candidate.py --config /private/bilibili-comments.json --state-dir /private/interaction-state --max-pages 3 --max-parents 10 --max-reply-pages 3
```

沿用当前私有互动状态目录，不另建相互不认识的账本。一级评论按时间查询；子回复单独分页，不把一级列表内的回复预览当作完整回复。每个作品及根评论分别保存分页位置；跨轮先更新第一页，再继续未读历史，旧根评论按上次检查时间轮转。页数范围为 2 至 10，父评论预算 1 至 50。未查完保持 partial，不能解释成“没有新留言”。回到历史末页不冒充从头重新遍历完成。

退出码：`0` 表示本轮所配置作品及已知父评论在预算内检查完成，`3` 表示部分覆盖，`2` 表示失败。`complete` 始终只指当前显式配置的作品，不代表整个账号或平台；新增作品须从正式分发账本补入配置。数字页码在评论变化时可能位移，重叠查询及重复去重不能保证原子快照，后续仍需补查。

真实评论 ID、作品 ID、根和直接父级均保存；不会从正文造 ID。同 ID 的作者、作品或父级冲突时拒绝改绑；原文变化会使已有草稿需要重审。历史基线在统一看板单独说明，不计已回复。模型上下文另标第三方读取及是否仍属于当前监测范围；收件箱缓存不等于实时原文。

同账号只允许一个本机巡检；其他账号可继续运行。HTTP 错误、重定向、验证码/拒绝响应、异常分页或缺失数据均停止本次扫描，保留旧记录；不切账号、代理或模拟人工规避。不输出 Cookie、原始错误响应或网友正文。不存在定时发送器或平台发送权限。

## 证据和后续验收

已在单账号的两个明确作品真实查询：一个视频返回空列表，另一个返回历史一级评论的稳定身份，子回复接口返回空列表；统一收件箱首轮写入一条历史基线，未发送。非空子回复分页、超出预算续读、轮转、身份与分页反例当前经离线测试；持续运行、完整账号覆盖、回复发送和其他账号仍待实测。

参考现有固定工具 [biliup v1.3.4](https://github.com/biliup/biliup/tree/95e67857f943f0ea90263668c79191784e94421a)：其 CLI 有 comments 和默认预览的 reply；仅运行默认预览不会验证登录或实际发送。CLI 的 comments 文本输出未保留完整分页与父子字段，本模块独立读取结构化响应，没有复制上游代码或增加依赖。上游 LICENSE 与 README 使用声明须分别审查；本次只读验证不解除平台规则和无人值守资格限制。

另行授权的私有自评论试点曾收到 `code=0`、成功提示与稳定评论 ID，但随后两次独立列表查询未出现该 ID。保留为“已受理、可见性未确认”，不重复发送，也未继续子回复；不能凭成功提示把回复计入已核验。原因尚未确定，不能直接归为审核拒绝。已知写入与列表证据不一致时，应保留提示并只读核查，不用空列表推断这次写入不存在。

该版本 CLI 的 reply 把 root 与 parent 同设为输入的 rpid。未来接统一发送器时，须分别保存根评论与直接父级，先核对当前原文和账号；一级评论试验不能代替楼中楼验收。[上游需求及作者实测](https://github.com/biliup/biliup/issues/1627)可作路线线索，不能代替当前账号的独立读回。
