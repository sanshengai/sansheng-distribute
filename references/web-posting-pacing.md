# 网页发布节奏（跨平台交错 + 不均匀间隔）

适用于作者已授权的网页路线（专用 Chrome）。**本文的任何做法都无法保证规避风控、限流或封号**；它只减少“整齐节拍、上传即发、多平台同秒操作”这类明显异于常人的信号。不使用反检测浏览器、改指纹、VPN/代理切换、清 Cookie、换号换 IP 重试等手段。X 的专项规则见 [x-web-posting-practice](x-web-posting-practice.md)；账本硬下限见 [pacing](pacing.md)。

## 2. 社区经验（未经官方确认，数字仅供参考）

- 抖音普通内容无公开硬上限；运营文章多建议新号每天 1–3 条、老号 ≤3 条，“作品间隔几个小时”；有称一天 20 条左右后审核变慢。来源均为工具商/运营号，口径不一：<https://a.newrank.cn/trade/news/2792>、<https://yimeizhushou.com/h-nd-336666.html>、<https://www.chanmama.com/yunyingquan/question/2555.html>、<https://zhuanlan.zhihu.com/p/2014358500654999234>（后者“老号 10 条内、健康分<70 降到 10 条”等数字**无官方出处**）。
- 同设备/同 IP：建议“一机一卡一号”、家用 WiFi 下设备不超过 4 台（newrank 同上）；视频号经验帖称同 WiFi 4–5 个号“基本没问题”：<https://zhuanlan.zhihu.com/p/538387760>。均为传闻。矩阵号“相同内容 + 同 IP 批量操作”被降权的说法：<https://zhuanlan.zhihu.com/p/2054222080246387143>。
- B站：UP 主自述一稿短时间内反复修改重传（约 8–10 次）后疑似隐形限流，建议 5 次后当天停止投稿/修改：<https://www.bilibili.com/opus/1003753489374904325>（个案，平台未承认）。
- 多平台分发本身不被禁止，风险来自“机器批量搬运、同质化”；建议每平台单独写标题描述、错峰：<https://a.newrank.cn/trade/news/8310>（工具商文章，所引“抖音白皮书”原文未核到）。
- 上传后停留多久、平台切换间隔多久才“安全”：**未找到任何可靠公开数据**。

## 3. 本 skill 的默认节奏（保守的个人估计，非平台规则）

配置：`assets/web-pacing.default.json`；私有 profile 可用 `web_pacing` 覆盖（同结构，只改需要的字段）。实现：`scripts/pacing.py`。

| 平台 | 上传后停留（秒，三角分布偏短） | 同平台发送间隔（对数正态） 中位 / 下限 / 上限（分钟） | 每日上限 |
|---|---|---|---|
| X | 30–180 | 25 / 12 / 90（σ 0.5） | 6 |
| 抖音 | 45–180 | 90 / 45 / 240（σ 0.45） | 3 |
| 视频号 | 45–180 | 90 / 45 / 240（σ 0.45） | 3 |
| 微博 | 30–150 | 40 / 20 / 150（σ 0.5） | 6 |
| B站 | 60–180 | 120 / 60 / 300（σ 0.45） | 3 |
| 小红书 | 60–180 | 120 / 60 / 300 | 2（**paused**，拒绝排队） |

全局：平台切换前随机等待 20–90 秒；同一时刻只做一个动作；最多同时 2 个已上传未发送的编辑页（`max_open_editors`，1–3）；同平台同时只有一个打开的编辑页。

依据：抖音/视频号/B站取社区“每天 1–3 条、间隔数小时”的偏保守端；微博、X 的文字与短视频节奏更快但仍远低于任何公开口径。代码硬下限：同平台发送间隔 ≥5 分钟、停留 ≥10 秒，配置无法再调低。

## 4. 调度规则（pacing.py）

1. 每个任务 = 上传 → 随机停留 → 发送。停留从上传完成算起，不足不发。
2. 编辑页未满 `max_open_editors` 时，优先去**另一个平台**上传，而不是立即发送刚上传的那条；刚上传的任务不会作为紧接着的下一个动作发送（若有其他可做或可等的动作）。
3. 同平台下一次上传要等上一次发送后的对数正态间隔（截断重采样，不是夹边，避免堆积在上下限）。
4. 当日（本机时区）已发送 + 已上传待发达到上限时，该平台余下任务不再开始，`next_action` 返回 `idle/daily_cap_or_blocked`，由作者顺延到次日，不压缩间隔。
5. 任何一步返回失败（验证码、“稍后再试”、登录跳转、读回不符……）→ 该平台本轮所有任务标为 `stopped`，不重试；其他平台继续。是否当天全停由作者决定。
6. 调度器不碰浏览器、Cookie、账本；实际动作仍由各平台执行器完成，账本 `pacing` 的预留窗口继续作为最后一道硬下限。

预览（只模拟，不动浏览器）：`python3 scripts/pacing.py --seed 1 S3E08-dy:douyin S3E08-x:x S3E08-wb:weibo`。

## 5. 仍然要做的

- 每平台文案、标签差异化；不跨平台逐字复制。
- 固定专用 Chrome 与网络；发布间隙不在平台上做无关自动化（刷流、点赞、关注）。
- 新号或刚出现过验证的账号，把每日上限减半、间隔中位数加倍。
